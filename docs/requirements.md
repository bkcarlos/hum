## 1. 项目背景与定位

### 1.1 背景
现有音乐平台的"猜你喜欢"是基于协同过滤的黑盒推荐，用户无法用自己的语言精确表达"我现在想听什么"（如"适合雨天加班的慵懒爵士，别太吵"）。大语言模型擅长理解这类自然语言描述，但**不能让 LLM 直接生成歌曲列表**——它会编造不存在的歌、张冠李戴。本项目的核心思路是让 LLM 负责"理解用户 + 排序筛选"，真实歌曲数据全部来自 Apple Music 官方 API。

### 1.2 产品定位
- **形态（v1 锁定）**：**纯网页版** Web 应用，桌面 + 移动端浏览器访问；前端用 MusicKit JS，对接 Apple Music HTTP API
- **v1 明确不做的形态**：不做 iOS/macOS 原生 app（Swift MusicKit）、不做 Wails/Electron 桌面端——既为收敛范围到 Vue 3 + Go，也为规避原生/桌面端的写接口限制（见 §6 风险）
- **用途**：个人自用，可免费分享给他人使用
- **明确不做**：不商业化、不收费、不接广告、不做内购（受 Apple MusicKit ToS 4.5.2 约束）
- **LLM 成本**：用户自带 LLM API key（BYOK），调用费用由用户自行承担，本应用不代付、不保存其 key
- **目标用户**：拥有 Apple Music 订阅、希望用自然语言精确探索音乐的人

### 1.3 合规边界（重要约束，非功能需求）
本产品受 Apple MusicKit 服务条款约束，以下为硬性红线：
- 音乐播放必须由用户主动发起，需提供标准播放控件（播放/暂停/跳过）
- 不得对访问 Apple Music 收费，不得通过广告、内购、售卖用户数据等方式间接变现
- 不得下载、上传、转发来自 MusicKit 的音乐文件
- 封面图、元数据仅可用于播放或歌单展示场景
- 完整播放要求用户本人持有有效 Apple Music 订阅，API 不绕过订阅
- 通过 API 创建的歌单默认私有，且 API 不支持将其公开/分享

### 1.4 UI 形态决策：左右双栏
v1 采用**左对话 + 右歌单操作**的双栏布局，让对话与列表各司其职、互不挤占。

```
┌─────────────────────┬──────────────────────┐
│  左栏 · 对话          │  右栏 · 歌单操作        │
│  懂你 & 微调          │  精确操作              │
│                     │                      │
│ · 自然语言输入        │ · 候选歌曲列表          │
│ · AI 回应/解释        │ · 试听 / 播放控件       │
│ · 追加微调            │ · 勾选 / 取消 / 全选     │
│  （"去掉有歌词的"）    │ · 建成歌单按钮          │
└─────────────────────┴──────────────────────┘
        左边"指挥"，右边"验收"，两栏联动
```

- **分工**：左栏对话负责理解需求与自然语言微调；右栏列表负责试听、精确多选、建歌单
- **联动**：左栏的对话指令（如"再慢一点""去掉有歌词的"）实时驱动右栏列表的换批/重排
- **为什么不用纯对话式**：建歌单 = 精确多选 + 试听 + 确认，是列表型操作；塞进聊天气泡里做多选/试听局促且易错
- **响应式降级（必须做）**：宽屏左右双栏；窄屏改为上下两区或 tab 切换，不可在窄屏并排
- **状态同步规则（需明确）**：右栏手动勾选后若左栏又触发新一轮推荐，需定义"覆盖"还是"追加"、已勾选项是否保留（详见 F10）

## 2. 核心概念与原则

### 2.1 黄金原则：LLM 不产歌，只懂人与排序

```
用户自然语言
   ↓  ① LLM 解析意图（输出结构化检索条件）
结构化意图：情绪 / 风格 / 乐器 / 节奏 / 关键词 / 种子歌手
   ↓  ② 调 Apple Music API 搜索（拿真实候选歌曲池）
候选歌曲池（几十~上百首真实歌曲）
   ↓  ③ LLM 筛选 + 排序（输入候选池，输出精选+理由+歌单名）
推荐结果（带推荐理由）
   ↓  ④ 用户试听 + 勾选
确认喜欢的歌
   ↓  ⑤ 写入 Apple Music 歌单
```

这是一个 RAG 思路：LLM 是"理解层"和"排序层"，Apple Music 是"事实层"。

### 2.2 术语表

| 术语 | 含义 |
|------|------|
| 候选池 | 由检索条件从 Apple Music 搜回的真实歌曲集合，未经 LLM 精选 |
| 意图（Intent） | LLM 把自然语言解析出的结构化检索条件 |
| 种子歌手 | 用户提供的参考歌手/歌曲，用于扩充候选池 |
| Developer Token | 后端用私钥签发的 JWT，证明你是 Apple 开发者 |
| Music User Token | 用户授权后拿到的令牌，用于读写该用户的资料库 |

### 3.2 功能详述

#### F0 · 用户自带 LLM 配置（BYOK）（P0）
采用**方案 B**：key 随请求传递给后端，后端用完即弃，不在服务器持久化。

首批支持的 Provider（后端三类适配器）：

| 类别 | 适配器 | 覆盖厂商（预设） |
|------|--------|--------------------|
| OpenAI 兼容 | `OpenAICompatProvider` | OpenAI、DeepSeek、Qwen/通义、Moonshot(Kimi)、智谱 GLM、MiniMax、OpenRouter 等 + 自定义 |
| Anthropic 原生 | `AnthropicProvider` | Claude（`/v1/messages`，`x-api-key` + `anthropic-version`） |
| Gemini 原生 | `GeminiProvider` | Google Gemini |

要点：
- 前端 Provider 下拉，预设默认 Base URL 与模型，选中后可改
- 配置项：Provider、API Key、（可选）Base URL、模型名
- 三层抽象：统一内部接口 `LLMProvider`（`ParseIntent()` / `RankSongs()`）+ 三个实现 + 前端预设表
- key 仅存浏览器本地（localStorage/IndexedDB），由用户掌控
- 「测试连接」按钮发最小请求验证 key
- 「清除配置」一键删除本地 key
- 每次 LLM 请求前端把 key 放入请求头随请求发给后端
- 后端**仅在单次请求生命周期内使用** key：用完即弃，绝不写库/缓存/日志
- 多 Provider 错误归一化（key 无效/余额不足/限流/模型不存在/网络不可达）
- 安全：key 只在单次请求内存；不写任何日志（access/error/trace 都排除 key 所在 header）；不缓存不复用；全程 HTTPS；依赖 TLS 不自行加密；排查 CDN/WAF/APM 隐蔽泄露

验收：
1. 填 key 并测试连接成功
2. 刷新后 key 仍在；清除后本地无 key
3. 代码审查确认无任何路径将 key 写入 DB/缓存/日志
4. 未配置 key 时 F3/F5 明确提示先完成 F0

#### F1 · Apple Music 授权登录（P0）
- "连接 Apple Music" → MusicKit JS 授权
- 前端拿 Music User Token，后端持 Developer Token
- 授权后读取用户 storefront，会话内随请求带给后端
- **Music User Token 不持久化**：仅当前会话（内存/sessionStorage），不落库；每次访问重新授权
- 未订阅用户明确提示，不在 app 内销售

验收：
1. 授权成功后能读到身份与 storefront，可调用需 user token 的接口
2. 关闭/刷新会话后 user token 不存在，需重新授权

#### F2 · 自然语言偏好输入（P0）— 左栏
- 多行 textarea，⌘/Ctrl+Enter 发送
- 首次进入预设快捷标签（心情、场景）破冰
- 可选"种子歌手/歌曲"输入位
- 提交后进入对话流，追加消息微调（F10）

#### F3 · LLM 意图解析与回显（P0）
- 后端调 LLM 解析为 `{ moods, genres, instruments, tempo, keywords, seed_artists }`
- 前端 chip 回显，可删改后再检索

#### F4 · Apple Music 候选歌曲检索（P0）
- 后端用结构化条件调 Catalog Search
- **storefront 跟随用户**（不写死）
- **id 一致性约束**：检索/试听/建歌单必须用同一 storefront
- 有种子歌手时额外扩充候选池
- 候选池 50~150 首，去重
- 缓存（key 含 storefront）

#### F5 · LLM 筛选排序与推荐理由（P0）
- 候选池喂回 LLM，输出 `{ playlist_name, description, songs:[{ id, reason }] }`
- 每首附简短推荐理由
- 验收：歌曲 id 必须来自候选池，不得编造

#### F6 · 歌曲试听（P0）— 右栏
- 优先预览片段；订阅用户走 MusicKit 完整播放
- 标准控件：播放/暂停/跳过
- 播放须用户点击发起

#### F7 · 勾选与歌单创建（P0）— 右栏
- 候选行勾选/取消、全选
- 确认后 `POST /v1/me/library/playlists`（用用户 storefront 的歌曲 id）
- 歌单名/描述默认用 LLM 结果，可改
- 默认私有，API 无法公开/分享，UI 须告知

#### F8 · 歌单历史与管理（P1，非 MVP）
- 记录生成过的歌单及原始 prompt；查看/重生成/删除（DELETE 在部分端有 401，需实测）

#### F9 · 品味记忆/个性化（P2，非 MVP）
- 记录勾选/跳过行为作为后续排序偏好上下文

#### F10 · 多轮对话式微调（P1，MVP）— 左栏核心交互
- 支持"再爵士一点""去掉有歌词的""换掉第二首"等追加指令
- 每轮把当前意图 + 追加指令交给 LLM，重检索/重排，更新右栏
- **状态同步规则（必须实现）**：
  - 默认**覆盖**候选，但**保留用户已勾选且仍在新结果中的歌**
  - 已勾选但不在新结果中 → 提示是否保留
  - UI 区分"本轮新换"与"上轮保留"

## 4. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 提交到出结果端到端 < 8 秒（含两次 LLM + 一次检索） |
| 可用性 | 解析/检索/排序任一步失败有清晰错误与重试入口 |
| 安全 | Developer Token 私钥仅后端；Music User Token 不落库明文；用户 LLM Key 仅单次请求内存、绝不持久化绝不写日志 |
| 隐私 | 不收集变现用户数据；最小化存储 |
| 兼容 | 桌面与移动浏览器；MusicKit JS 授权与播放主流浏览器实测（含移动端 Safari），M1 验证 |
| 成本 | LLM 用量缓存与限流；Apple Music 调用缓存 |
| 可维护 | LLM Provider 与音乐 Provider 抽象为接口 |

## 5. 技术架构

### 5.1 总体架构

```
Vue 3 前端 (MusicKit JS)
   │  · 本地存储用户 LLM API Key (localStorage/IndexedDB)
   │  · 每次请求将 key 放入请求头
   │  HTTPS
   ▼
Go 后端（编排层 Gin/Echo）
   ├─→ LLM API（用请求头里的用户 key；用完即弃，不落库不记日志）
   ├─→ Apple Music API（Catalog 搜索 / 创建歌单）
   └─→ 存储：SQLite/PostgreSQL（歌单历史）+ 可选 Redis（缓存）
          ⚠️ 存储与缓存中均不得包含用户 LLM Key
```

### 5.2 技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | Vue 3 + Vite + TS + Pinia | Pinia 分管"对话状态"与"列表状态"并处理联动 |
| 布局 | 左右双栏 + 响应式降级 | 宽屏双栏；窄屏上下/tab |
| UI | Naive UI（本脚手架选定） | 原文为 Naive UI 或 Element Plus 二选一 |
| 播放/授权 | MusicKit JS | 拿 user token、播放 |
| 后端 | Go + Gin（本脚手架选定） | 原文为 Gin/Echo |
| Developer Token | Go ES256 私钥签 JWT | 后端签发，有效期 ≤ 6 个月 |
| LLM | 用户自带（BYOK），全 Provider | 三类适配器 |
| LLM Key 传递 | 前端本地存储 + 请求头携带 | 后端单次使用、用完即弃（方案 B） |
| 存储 | SQLite 起步 | 不存 LLM Key |
| 部署 | 前端静态托管 + 后端单 Go 服务 | 纯网页；HTTPS 必备 |

### 5.3 认证流程（Apple Music 两层 Token）
1. 后端用 .p8 私钥 + ES256 签 **Developer Token**（JWT）
2. 前端 MusicKit JS 用 Developer Token 初始化，引导授权
3. 授权后前端拿 **Music User Token** 与用户 **storefront**
4. 涉及资料库的请求同时带 Developer Token + Music User Token
5. **Music User Token 不持久化**：仅当前会话；会话结束失效，重新授权
6. 检索/建歌单全程同一用户 storefront（id 一致）

### 5.4 关键外部接口

| 用途 | 接口 |
|------|------|
| 目录搜索 | `GET /v1/catalog/{storefront}/search` |
| 歌曲详情 | `GET /v1/catalog/{storefront}/songs/{id}` |
| 创建歌单 | `POST /v1/me/library/playlists` |
| 歌单加歌 | `POST /v1/me/library/playlists/{id}/tracks` |

### 5.5 两次 LLM 调用的数据契约

① 意图解析：
```json
{
  "moods": ["慵懒"],
  "genres": ["爵士"],
  "instruments": ["钢琴", "萨克斯"],
  "tempo": "slow",
  "keywords": ["雨天", "加班"],
  "seed_artists": []
}
```

② 筛选排序：
```json
{
  "playlist_name": "雨夜爵士加班室",
  "description": "慵懒钢琴与萨克斯，陪你度过加班的雨夜",
  "songs": [
    { "id": "1440...", "reason": "舒缓钢琴主导，节奏慵懒契合雨天氛围" }
  ]
}
```

## 6. 关键风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| ToS 禁止变现 | 无法回本 | 定位自用/免费分享；99 美元当门票 |
| 用户需自有订阅 | 受众受限 | UI 告知；不在 app 内销售 |
| 歌单无法 API 公开 | 不能分享 | 不做分享；引导去 Music App 手动改 |
| 部分端 DELETE 401 | 删除受限 | v1 纯网页已规避；删除延后并实测 |
| MusicKit JS 浏览器兼容 | 授权/播放失败 | M1 目标浏览器实测；降级提示 |
| LLM 产池外/编造歌曲 | 推荐不可用 | 强约束 id 来自候选池；后端校验过滤 |
| 试听预览缺失 | 体验下降 | 订阅走完整播放；预览补充 |
| LLM/检索延迟高 | 体验差 | 缓存、并行、loading 文案 |
| 用户 LLM Key 泄露 | 严重安全事故 | 不落库不进日志；header 排除；HTTPS；审查 + grep |
| 未配置/key 无效 | 无法使用 | F0 测试连接；F3/F5 前置校验 |
| 本地 key 被同设备他人读取 | 局部风险 | 提示勿在公共设备保存；一键清除 |
| 双栏状态同步混乱 | 用户困惑 | 明确同步规则：覆盖+保留已选+变更提示 |
| 移动端双栏挤压 | 小屏不可用 | 响应式降级；M2 验证窄屏 |

## 8. 验收标准（MVP 整体）

拥有 Apple Music 订阅的用户能够：
1. 浏览器中连接并授权 Apple Music
2. 填入 LLM API Key 并测试连接成功（key 仅本地、服务器不保存）
3. 输入自然语言描述（或点选快捷标签）
4. 看到可编辑的意图标签
5. 获得来自真实曲库、带理由的歌曲列表
6. 试听歌曲
